Yorikado / 運用・障害対応
=======================
1. 日常の運用
  - 定期ジョブ: /api/v1/internal/jobs/run を1〜5分ごと（Cron）。処理内容:
      通知（アプリ内＋組織設定でメール）、招待メール、未回答の催促（09:00〜18:00 JST、1店舗1日1通知へまとめる、送信直前に回答済みを再確認）、
      組織データ出力、印刷データの期限削除（24h・有効化・破棄後）、確認画面の期限切れ整理。
      失敗は指数バックオフ（1,2,4,8分）で最大5回、超過は outbox.status='failed'（失敗キュー）。dedupe_key で二重送信を防止。
  - 失敗キューの確認（SQL, service role）:
      select kind, count(*), max(last_error) from outbox where status = 'failed' group by kind;
    原因を直したら再送: update outbox set status='pending', attempts=0, next_attempt_at=now() where id = '<id>';
  - レート制限の値（src/server/ratelimit.ts）は暫定。繁忙時の実測（ピーク時の券確定回数/分）で調整し、変更は記録する。
  - 照会失敗が多い店舗は事務局（管理者・承認者）にアプリ内通知「照会・ログインの失敗が多く発生しています」。

2. 定型の事務局作業（画面）
  - 月次精算: 地域券 → 精算・照合 → 対象月で「集計して精算案を作る」→ 例外を解消 → 承認を依頼 → 承認者が承認
    → 支払作業票を出力（銀行に取り込めるファイルではない。銀行の画面で振込）→ 銀行の結果を所定CSV（line_id, bank_reference, amount_jpy, result, executed_date）に変換して取込
    → 取り込んだ人と別の担当者が「照合結果を確定」→ 要確認の行は承認者が判断を記録して解消。
  - 再出力は同じ内容hashで「再出力」と明記されます。銀行で重ねて振込しないこと。
  - 支払後の取消: 次の精算に負の調整として現れます。回収・相殺は運営判断として別承認で記録（自動引落しはしない）。

3. 障害対応
  症状と一次対応
  - 「結果を確認しています」が多発: DB/ネットワーク遅延の可能性。Supabase のステータス・アプリログ（requestId）を確認。
    店舗には「新しく読み直さず、受付番号付きで相談」を案内。operations テーブルで idempotency_key を検索して確定有無を回答できます。
  - 券が「使用済み」と出るが店に記録がない: 他店で使用済み（店名は表示しない仕様）。事務局で coupons.redeemed_operation_id → redemptions を確認。
  - 流出の疑い: 事業詳細 → 発行バッチ「紛失・流出で失効させる」（未使用券を void）。必要なら事業を「受付を停止する」。
  - 端末紛失: 本人「すべての端末からログアウト」、または管理者がメンバーの役割を外す（事務局セッションは失効）。
    TOTP 端末の紛失: 管理者が Supabase の Auth 管理画面で当該ユーザーの MFA 要素を削除し、本人が /mfa で再登録（本人確認を記録）。
  - 銀行結果の誤取込: 確定前なら取込を破棄して取り直し（同一ファイルは同じ取込を返す）。確定後は要確認行の判断記録で対応し、行を直接変更しない。
  インシデント連絡: 契約者（商店街・事務局）の担当窓口、運営の技術窓口、（実券時）発行者。連絡網は導入時に docs/legal/ROLES_DRAFT.txt で確定。

4. バックアップ・復元
  - LIVE は Supabase の有料プランで日次バックアップ＋PITR を有効化することが前提。添付（Storage）は別途日次バックアップ。
  - 初期運用目標: RPO 24時間 / RTO 8時間（目標値。実測ではない）。
  - 復元訓練（ローカルDEMO）: npm run backup:check
      DB を pg_dump(custom) → 新しいDBへ pg_restore → 全テーブル行数・精算合計（batch/lines/sources）・添付ファイルの SHA-256 を照合し、所要時間を記録。
    ホスティング上の LIVE 復元は新しいプロジェクトへ PITR 復元し同じ照合を行うこと（導入時に実施・記録）。

5. 保存期間（初期の製品設定。法定保存義務を断定するものではない）
  取引・精算・監査 7年 / 回覧・回答・相談 2年 / 写真 1年 / 失敗ジョブログ 90日 / セキュリティログ 180日。
  - outbox の送信済み30日・失敗90日は svc_housekeeping が削除。
  - 期限削除（対象一覧→承認→実行→監査）は v1 で未実装。契約前に責任者が保存方針を確定し、legal hold 対象は削除しないこと。
  - 退会: 店舗を「退会」にしても履歴は残る（アクセスのみ失効）。個人連絡先の匿名化は保存方針確定後に手順化。

6. DEMO と LIVE の分離
  別 Supabase プロジェクト・別 Storage・別シークレット・別ドメイン。DB の deployment_environment と APP_ENV が一致しないと verify-env が失敗。
  DEMO リセット（npm run db:reset:demo）はローカルのみ。LIVE をリセットするスクリプトは提供しない。
